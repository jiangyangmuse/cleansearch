**验收标准**

## 2 做了什么

1. 重新拉起 SearXNG（源码 + venv + Windows shim），逐引擎探测发现：`bing/google/yahoo/sogou` 默认 **disabled**，请求会被忽略并回落默认集——这就是「指定 startpage 却返回 google cse」的根因。
2. 在 SearXNG settings 显式启用 `bing/yahoo/sogou`；实测 `google cse / yahoo / sogou` 可独立出结果，`bing` 空、`sogou` 在 SearXNG 侧 crash。
3. 产品与验收脚本补后缀：`gc`(google cse)、`y`(yahoo)、`sg`(sogou)、`sp`(startpage)、`mj`(mojeek)；回归集补 5 条（共 45 条）。
4. 修缓存写入条件：原来要求「没有任何不可用引擎」，真实上游永远不满足 → 缓存从未写入。改为「有结果就缓存」，命中时保留 `meta.unresponsive`，并加回归测试。
5. 采集验收证据：指定引擎 9/9、默认质量 8/8、冷热缓存对照、真实搜索接千问、本地重启持久化。
6. 文档同步：README 引擎表与实测数字、决策 M9-D14…D17、进展与欠账 P0-1 置完成 / P0-2 置部分完成、六阶段报告追加更正。

## 5 关键决策

| 决策 | 备选 | 理由 |
| --- | --- | --- |
| 在 SearXNG settings 里显式启用 yahoo/sogou | 只用 google cse 硬凑 | disabled 引擎会被上游忽略并回落默认集，不启用就永远验收不过 |
| 新增 `gc/y/sg/sp/mj` 后缀 | 把 `g` 直接映射到 google cse | `g` 的语义是 Google；换个 id 会误导用户，新后缀更诚实 |
| 缓存改为「有结果就写」 | 保持「无失败引擎才写」 | 真实上游永远有失败引擎 → 缓存永远不生效，冷热对照无法成立 |
| P0-2 标部分完成 | 声称 Compose 已验证 | 无 Docker 就是没跑过，不能写通过 |
| 千问显式 `LLM_REASONING_EFFORT=none` | 提高超时硬等 | 推理模式会把首字拖到超时；关掉推理才符合「摘要」用途 |

## 6 遗留与风险

- `sogou` 在 SearXNG 侧会 crash，暂时不可依赖；`bing` 空、`brave` 限流、`ddg` CAPTCHA。
- 验收依赖仓库外的 SearXNG 源码、venv 与 settings；换机器需重做（README 有步骤）。
- 千问只测了一条查询的 fast 路径；首字 7.7s 高于设计目标（2.5–4s），full 路径未测。
- 缓存命中时仍展示 `meta.unresponsive`，用户可能误以为这次也失败了。
- Compose 与卷持久化、正式浏览器、Android 仍未验证。
