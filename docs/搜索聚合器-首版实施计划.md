# 干净搜索聚合器 · 首版实施计划

> 2026-11-05 · 开工建议 · 配套文档 [《搜索聚合器构建方案》](搜索聚合器-构建方案.md)

首版面向本机单用户。先验证「启动服务 → 输入查询 → 看见结果 → 打开链接」，再加三档相关性、AI 侧栏和书签启动台。正文抓取通过安全测试后，再开放依赖它的功能。

## 框架与职责

- **前端使用 React + TypeScript + Vite。** 搜索页、结果页和书签页采用客户端渲染。开发时由 Vite 代理 `/api`，发布时由 FastAPI 同源提供前端静态文件和 API，并支持直接刷新前端路由。如果后续确定需要为公开页面做服务端渲染，再评估 Next.js。
- **SearXNG 负责引擎并发，FastAPI 负责查询与结果处理。** FastAPI 每次搜索向 SearXNG 发送一次聚合请求，并负责后缀解析、结果归一化、去重、过滤和分组。先在部署机器实测 2–3 个引擎，再决定是否接入一个商业供应商兜底。用户显式指定引擎时，该引擎不可用就明确提示，并由用户选择切换。
- **SQLite 先持久化书签和分组。** 搜索快照在单进程内存中短期保存，设定容量上限和过期时间，供侧栏总结读取。书签先按标题和 URL 搜索，出现全文检索或跨进程共享需求后，再分别引入 FTS5 或持久缓存。
- **首版服务入口仅绑定本机。** Compose 中 FastAPI 通过 `http://searxng:8080` 访问内部 SearXNG 服务。开放局域网访问前补齐鉴权。搜索端点统一使用 `POST /api/search` 和 JSON 请求体。

## 实施顺序与验收

| 阶段 | 实现内容 | 验收标准 |
| --- | --- | --- |
| **M0 搜索闭环** | 在实际部署机器验证 SearXNG。搭建同源前后端、`POST /api/search`、最小结果列表和本机启动命令。 | 能通过浏览器提交查询并打开结果。固定样本能稳定验证结果页。区分有结果、零结果和上游不可用三种状态。 |
| **M1 搜索体验** | 加入后缀路由、URL 去重、已知恶意链接拦截和三档分组。初始排序使用标题与摘要匹配、引擎排名和来源共识。 | 用 30–50 条常用查询做回归，覆盖 `C g`、地区后缀、全弱结果和黑名单命中。`C g` 保持普通查询，地区后缀单独解析，强相关栏允许为空，已知恶意链接直接拦截。 |
| **M2 AI 侧栏** | 用户点击「生成总结」后，使用本次搜索中通过过滤的摘要发起一条 SSE 流。引用绑定稳定的 `result_id`，切换查询时取消旧流。 | 结果列表先显示。结果重排后引用仍能跳到对应卡片。模型超时后仍能继续搜索和打开结果。 |
| **M3 书签启动台** | 支持结果卡一键收藏、分组、搜索和浏览器 HTML 导入导出。 | 导入再导出后保留 URL、标题和分组。重复导入按明确规则处理。 |
| **M4 正文增强** | 先实现统一的受控抓取入口，再开启搜索正文增强、单页总结和死链检测。 | 阻断访问非公网地址的请求，包括重定向目标。限制响应大小和抓取耗时。正文不可用时，搜索总结保留摘要版并标明素材来源。 |

## 第一批开发任务

1. **先验证上游。** 启动 SearXNG 并开启 JSON 响应，用常见中文、英文和短关键词查询验证 2–3 个引擎，记录成功率、延迟及失败表现。
2. **再确定接口和状态。** 用固定响应样本打通 `POST /api/search`，接入 SearXNG 后确认成功、零结果和上游不可用能在页面上清楚区分。
3. **最后打通本机使用。** 接上搜索框、结果列表和原站链接，从浏览器跑完一遍搜索闭环，补齐本机启动命令和冒烟检查。

第一批开发以 M0 验收为交付点。向量排序、LLM 重排、PWA、浏览器扩展和桌面壳等主链路稳定后，再按使用反馈选做。商业兜底根据实测的引擎可用性决定。
